# 事実の置き場

目標は**機械化**。事実を、機械が読める1つの持ち主に置き、文書はそれを指す。写しが減るのは結果で、目的ではない。

エージェントに記録を任せると文書は増え、**同じ事実が2箇所に書かれた時点から片方が古びる**。ただし写しを消すこと自体を目的にすると、持ち主の無い事実まで消して知識を失う。順番を守る。

## 順番

1. **機械が読める持ち主に置けるか。** 一覧・関係・設定値・対象範囲は、たいてい宣言に置ける——変数、検索条件、スキーマ、カタログの entity と edge。置けるならそこが持ち主で、文書は指すだけにする。写した時点で、以後ずっと2箇所を直す約束をしたことになる。
2. **持ち主が無いなら、作れるか。** 散文に一覧があるのは「持ち主を作れない」証拠ではなく、たいてい「まだ作っていない」証拠。作る判断はユーザーに渡す——文書を直す作業の中で勝手に構造を増やさない。
3. **作れないものだけが散文に残る**——禁止（「これをすると 422 になる」「ローカルで実行しない」）、踏んだ失敗、他リポジトリとの契約、機械化できない判断。**これらは消さない。** どのファイルのコメントにも収まらず、事前に届いていないと意味がない。

**関係は散文で説明しない。** 何が何に依存し、ある変更がどこに届くかは、entity と edge にすれば、人が見る図とセッションが引く索引を同じ実体から出せる。散文で書くと、両方の用途に対して古びる。

## 外部に向けた文書は別

公開している repo の README や `docs/` は、その repo を**使う人**に向けたもの。CLI のオプションや設定ファイルの形式は、持ち主がコード側（パーサやスキーマ）にあっても、そこを指さずに書く。「詳細は `<file>` のコメント」は repo の中を読む人にしか届かない。OSS の repo はまるごとこちら側に来る。

## 基準

1. **持ち主は、それが間違っていると壊れる場所。** 設定の制約はその設定ファイル、CI の認証はその workflow、値の一覧はそれを定義している宣言。そこのコメントが理由を持つ。
2. **一覧・表・件数を散文に持たない**（「対象は A・B・C の3つ」「今は4本」）。増減を決めているものを指す。列挙は、片方だけ増やしたときに必ずずれる。
3. **リポジトリをまたぐ事実を、片方の散文に置かない。** 両方の当事者が必ず読むもの（双方のコメント、契約そのもの）に置く。互いに「相手が持っている」と書くと、実際にはどちらも持っていない状態になる。
4. **指示ファイルは push、それ以外は pull。** 毎セッション届くのは指示ファイルだけで、README・MCP・外部の文書は訊かれない限り読まれない。散文に残ると決めたものの置き場はこれで決まる。

## 消しすぎない

- 方針が実際に変わって追随した散文。写しではない
- 写しを防いでいる規範そのもの

## 棚卸しの手順

1. **drift の実績を履歴から出す。** 推測で始めない。指示ファイルと README を同時に触った commit、節ごとの書き換え回数を見る。churn が集中している節が、他所の写しを抱えている
2. **散文の主張ごとに、持ち主があるか確かめる。** あれば消す候補。無ければ消さず、**持ち主を作れるか**を見て候補として挙げる。変数名から察せるだけのものは「無い」として扱う
3. **写しが残りやすい形を探す。** 件数（「N つ」「N 本」）と実体の数の食い違い、ディレクトリの中身や変数の値を写した表、実在しないファイルへの参照。**その表を更新する手順がどこにも書かれていない表は、次に増えたときに必ずずれる**
4. **他のリポジトリと突き合わせる。** 同じ事実を主張している文書とコメントを探し、食い違いを見る。「あちらが決めている」と書いている先が**本当にそれを持っているか**も確かめる（移動していることがある）
5. **消す前に、持ち主にあるか確認する。** 無ければ**先に持ち主へ1行足してから**消す。手順を消すときは特に漏れやすい。コメントに移すときは、そのプロジェクトのコメントの長さの決まりに収める。収まらないなら README か ADR に置き、コメントはそこを指す
6. **「消したもの ↔ 既にある場所」の表で報告する。** レビューはこの対応だけを見れば済む。削除の量ではなく、対応が付いているかが判断材料になる

## 落ちやすいところ

- **自分が書いた要約が、直前の段落や別の節の言い換えになっていないか。** 写しを消す作業は、写しを作りやすい
- 削減率を目標にしない。重複だけを消した結果が数%なら、その文書はもともと健全だった
