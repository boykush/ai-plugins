# 文書の事実の置き場

エージェントに記録を任せると文書は増える一方で、**同じ事実が2箇所に書かれた瞬間から片方が古びる**。どう書くかより先に、置き場を1つに決める。

## 基準

1. **すでにどこかに書かれている事実を、散文に写さない。** 写す代わりに、それを持つファイルを指す。写した時点で、以後ずっと2箇所を直す約束をしたことになる。
2. **事実の持ち主は、それが間違っていると壊れる場所。** 設定の制約はその設定ファイルのコメント、CI の認証はその workflow のコメント、値の一覧はそれを定義している宣言。文書はそこを指すだけにする。
3. **一覧・表・件数を散文に持たない**（「対象は A・B・C の3つ」「今は4本」）。増減するものは、増減を決めているもの（変数・検索条件・discovery のクエリ）を指す。列挙は、片方だけ増やしたときに必ずずれる。
4. **リポジトリをまたぐ事実を、片方の散文に置かない。** 両方の当事者が必ず読むもの（双方のコメント、契約そのもの）に置く。互いに「相手が持っている」と書くと、実際にはどちらも持っていない状態になる。
5. **AGENTS.md は push、それ以外は pull。** 毎セッション届くのは AGENTS.md だけで、README・MCP・外部の文書は訊かれない限り読まれない。「これをすると壊れる」は訊かれる前に届いていなければ意味がない。
6. **AGENTS.md に置くのは、どれか1つのファイルには収まらないものだけ**——横断する禁止、踏んだ失敗、他リポジトリとの契約。手順と構成値は README、個々のファイルの理由はそのファイルのコメント。

## 消さないもの

- **禁止**（「これをすると 422 になる」「ローカルで実行しない」）と、**踏んだ失敗の記録**。どのファイルのコメントにも収まらず、事前に届いていないと意味がない
- 方針が実際に変わって追随した散文。写しではない
- 写しを防いでいる規範そのもの

## 棚卸しの手順

### 1. drift の実績を履歴から出す（推測で始めない）

どこに写しがあるかは、churn が集中している場所が教える。

```sh
# docs を触った commit の割合と、README と AGENTS.md を同時に触った commit の数
git log --no-merges --format=%h --since=<date> | while read -r h; do
  f=$(git show --name-only --format= "$h")
  a=$(printf '%s\n' "$f" | grep -c '^AGENTS\.md$')
  r=$(printf '%s\n' "$f" | grep -c '^README\.md$')
  [ "$a" -gt 0 ] && [ "$r" -gt 0 ] && echo "$h 両方"
done
```

節ごとの書き換え回数も見る（diff の hunk 開始行を見出しに割り当てる）。churn の集中した節が、他所の写しを抱えている。

### 2. 各事実の持ち主を確かめる

散文の主張を1つずつ取り、その事実が**使用地点に書かれているか** grep する。書かれていれば消す候補、書かれていなければ残す候補。推論で辿れるだけ（変数名から察せる等）は書かれていないものとして扱い、残す。

### 3. 機械的に見つかるもの

```sh
# 存在しないパスへの参照。他リポジトリのパスは正当なので、残ったものを目で分ける
git ls-files '*.md' | xargs cat | grep -oE '`[A-Za-z0-9_./-]+\.(md|ya?ml|tf|toml|json)`' | tr -d '`' | sort -u \
  | while read -r p; do [ -e "$p" ] || echo "無い: $p"; done
```

- 件数（「N つ」「N 本」）を、ディレクトリや変数の実体の数と突き合わせる
- 表が、ディレクトリの中身や変数の値を写していないか見る。**その表を更新する手順がどこにも書かれていない表は、次に増えたときに必ずずれる**

### 4. リポジトリをまたぐ矛盾

同じ事実を主張している他リポジトリの文書とコメントを grep し、食い違いを探す。「あちらが決めている」と書いている先が**本当にそれを持っているか**も確かめる（移動していることがある）。

### 5. 消す前に、持ち主にあるか確認する

無ければ**先に持ち主へ1行足してから**消す。手順を消すときは特に漏れやすい。コメントに移すときは、そのプロジェクトのコメントの長さの決まりに収める。収まらないなら README か ADR に置き、コメントはそこを指す。

### 6. 「消したもの ↔ 既にある場所」の表で報告する

レビューはこの対応だけを見れば済む。削除の量ではなく、対応が付いているかが判断材料になる。

## 落ちやすいところ

- **ローカルのブランチが古いまま編集すると、stale な base に当たる。** 枝は origin の default branch から切り、編集前に base を確かめる
- **自分が書いた要約が、直前の段落の言い換えになっていないか。** 写しを消す作業は、写しを作りやすい
- 削減率を目標にしない。重複だけを消した結果が数%なら、その文書はもともと健全だった
